# Spec: Plugin id `nixarchy.hyprlandsettings` and a NixOS-first README

## Design

### 1. Id rename (code)

| File | Change |
|---|---|
| `manifest.json` | `"id": "nixarchy.hyprlandsettings"` |
| `Service.qml` | `pluginId` fallback `"aziz.hyprforge"` → `"nixarchy.hyprlandsettings"`. Everything else already uses `pluginId` (launcher `Exec=`, `open`/`close`/`toggle`/`section`) |
| `Panel.qml` | `hide(… \|\| "aziz.hyprforge")` fallback → the new id |
| `Engine.js` | the `HEADER` line "generated by the aziz.hyprforge Omarchy plugin" → "generated by the nixarchy.hyprlandsettings plugin" |
| `flake.nix` | link `xdg.configFile."omarchy/plugins/nixarchy.hyprlandsettings"`; keybinding `toggle` targets the new id; comments |
| `skills/hyprforge/SKILL.md` (from #3) | the install check selects `.id=="nixarchy.hyprlandsettings"` |
| `AGENTS.md` (from #3) | invariant 1 lists the new id, noting that it replaced `aziz.hyprforge` in this PR |

**Unchanged:**
- the state paths (`~/.config/hypr/hyprforge{.lua,/}`,
  `~/.cache/hyprforge`, `hyprforge.desktop`), which aren't derived from the
  id, so settings, profiles and history carry over;
- the IPC target `hyprforge`;
- `hypr.hyprforge` and the hook;
- `X-Hyprforge-Managed`, `hyprforgeProfile` and `hf:*`;
- the skill's *name* (`hyprforge`): it's the command vocabulary.

The launcher file keeps its path and marker. The new service rewrites it
with `Exec=… toggle nixarchy.hyprlandsettings`.

### 2. Migration (existing installs), verified against Omarchy's scripts

`omarchy plugin disable <id>` goes through the shell's `setPluginEnabled`,
which fails with "not known" once the plugin is gone. So the order matters:

1. `omarchy plugin disable aziz.hyprforge`, while the old one is still
   installed.
2. `mv ~/.config/omarchy/plugins/aziz.hyprforge ~/aziz.hyprforge.old`, out
   of the plugins dir. Skip this if the old one was HM-managed (PR #1's
   module); the switch removes that symlink.
3. Switch the Home Manager / NixOS configuration. This links
   `nixarchy.hyprlandsettings`.
4. `omarchy-shell shell rescanPlugins`, then wait until
   `omarchy-shell shell ping` answers. No restart (see §4).
5. `omarchy plugin enable nixarchy.hyprlandsettings`.

Omarchy's catalog finds plugins with `find -L`, so the HM symlink is
discovered.

### 4. Shell-restart safety (the README part of the approved restart-safety intent)

- Measured on this host (2026-09-29, one shell process, no restarts):
  - swapping the plugin folder (a real dir becoming a symlink, then a
    retarget) makes the running shell hot-reload;
  - the shell stops answering IPC for about 8–30 s, while the bar stays up;
  - the plugin reappeared by itself after 30+ s.
- An `omarchy restart shell` issued during that window is what lost the
  race (nixarchy #953) and left no shell for 17 min.
- So the README never says "restart the shell" after install or update.
  It says: run `omarchy-shell shell rescanPlugins`, then wait until
  `omarchy-shell shell ping` answers. It gives a one-line wait loop, and
  points to nixarchy #953 for the background.
- `AGENTS.md` and the skill get the same rule. That lands in the
  restart-safety PR (its own spec), not here.

## Alternatives rejected

- **Automatic `shell.json` migration** (the service detects the old entry):
  declined at intent (Q2).
- **Renaming the state paths too**: no benefit, and it would force a data
  migration. Excluded at intent.
- **`omarchy restart shell` after a switch**: this is what caused today's
  outage. `rescanPlugins` plus waiting is the non-racy path.
- **A separate README PR**: it would conflict with every open PR. This one
  is last in the chain.

## Risks

- **A stale `aziz.hyprforge` entry:** if step 1 is skipped, `shell.json`
  keeps it. That's harmless (no plugin carries the id), but
  `omarchy plugin disable` can no longer remove it. What actually works in
  that case is verified during implementation and documented.
- **User keybindings** that call `toggle aziz.hyprforge` stop working. The
  HM binds are regenerated; a hand-made binding needs editing. The README
  says so.
- **Force-pushing #2/#3/#4** rewrites open PR branches. They're this
  user's own branches with no other contributors.
- **The live migration test touches this host's shell.** It follows §4
  (no restarts; wait for `ping` before each IPC step), and the agent bus is
  checked and announced first, as the host's hook requires.
